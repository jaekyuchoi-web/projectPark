# 2026년 2분기 누적 특수관계자 명세서 출력 설계

- 작성일: 2026-07-21
- 대상 앱: `hg-affiliate-app`
- 상태: 사용자 설계 승인 완료, 구현 계획 작성 전 문서 검토 대기

## 1. 최상위 회계기간 불변조건

> **절대 변경 금지:** 이 앱에서 분기는 독립된 3개월 구간이 아니라 회계연도
> 1월부터 해당 분기 말까지의 누적(YTD) 기간이다.

| 선택 분기 | 반드시 포함할 거래월 | 반드시 제외할 같은 해의 다음 달 |
|---|---|---|
| 1분기 | 1월~3월 | 4월 이후 |
| 2분기 | 1월~6월 | 7월 이후 |
| 3분기 | 1월~9월 | 10월 이후 |
| 4분기 | 1월~12월 | 없음 |

따라서 **2026년 2분기 상세 거래는 2026년 1월 1일부터 6월 30일까지**다.
4월~6월만 채택하는 구현은 명백한 결함이다. 다른 연도의 거래도 선택 기간에
포함하지 않는다.

이 규칙은 `Period` 도메인 모델 한 곳에서만 계산한다. 집계, 상세 거래, 출력 라벨,
검증 코드가 각자 분기 범위를 다시 계산하거나 별도의 월 목록을 갖지 않는다.

## 2. 문제와 확인된 근본 원인

`testrun/`의 1)~5) 입력과 화면에서 선택한 `Period(2026, 2)`로 현재 파이프라인을
재현한 결과는 다음과 같다.

1. 원장 추출은 정상적으로 2026년 1월~6월을 채택한다.
2. 2분기 추출 결과는 1분기 추출 결과를 포함하며, 실제로 1분기보다 더 많은 행을
   채택한다.
3. `run_pipeline()`은 필터링된 원장을 집계에 사용한다.
4. 그러나 `build_statement()`에는 선택 기간과 필터링된 상세 원장을 전달하지 않는다.
5. `fill_statement_template()`은 고정 자산
   `app/assets/statement_template.xlsx`의 `39.1` 시트를 그대로 보존한다.
6. 그 고정 템플릿에는 2026년 1분기 상세 거래와 1분기 표식이 남아 있다.

그 결과 현재 출력은 `39.2`에 주입되는 집계값과 `39.1` 상세 거래의 기준 기간이
서로 다를 수 있다. 이는 단순한 표시 오류가 아니라 한 파일 안의 데이터 계보가
불일치하는 문제다.

기존 기간 선택 설계의 비목표였던 “출력물 기간 라벨 자동 삽입”과, 고정 템플릿의
상세 거래를 재생성하는 테스트가 없었던 점이 이 결함을 허용했다.

## 3. 검토한 접근

### 3.1 채택: 단일 YTD 원장으로 집계와 상세를 함께 생성

`extract_current_period()`가 반환한 동일한 원장 프레임을 다음 두 소비자에게 전달한다.

- 기존 38.x 집계
- `39.1` 상세 거래 재작성

기간 계산과 데이터 계보가 하나이므로 집계와 상세가 서로 다른 분기를 가질 수 없다.
고정 템플릿은 보고서 양식과 서식을 제공하지만, 과거 분기의 상세 데이터는 제공하지
않는다.

### 3.2 기각: 템플릿의 `1Q` 문자열만 `2Q`로 치환

상세 행 자체가 1분기 자료이므로 라벨만 바꾸면 잘못된 데이터를 2분기로 표시하게 된다.
또한 2분기 누적 원장에는 정상적인 1분기 거래가 포함되며, 그 실제 적요에 `1Q`가 들어갈
수 있다. 전역 문자열 치환은 정상 적요를 훼손한다.

### 3.3 기각: 분기별 고정 템플릿을 별도 관리

분기마다 운영자가 템플릿을 교체해야 하고, 잘못된 분기 템플릿을 배치하면 같은 문제가
재발한다. 기간 선택값과 템플릿 파일 사이의 정합성을 자동으로 보장할 수도 없다.

## 4. 목표와 비목표

### 목표

1. 2026년 2분기 집계와 `39.1` 상세 거래를 모두 1월~6월 누적으로 생성한다.
2. `특관자`, `39.1`, `39.2`가 동일한 필터링 원장을 사용하게 한다.
3. 고정 템플릿의 과거 1분기 상세 데이터를 새 출력에 남기지 않는다.
4. 출력에서 선택 기간과 누적 월 범위를 명시적으로 식별할 수 있게 한다.
5. 분기 누적 정의를 코드, 테스트, README, 에이전트 지침에 강하게 고정한다.
6. 최종 파일을 `testrun/당기_특관자_명세서_2026_2Q.xlsx`로 생성한다.

### 비목표

- 전기를 같은 해 직전 분기로 바꾸지 않는다. 전기는 계속 전년도 온기/4분기다.
- 당기말 잔액명세서를 거래일로 필터링하지 않는다. 잔액명세서는 선택 분기말의
  스냅샷 입력을 그대로 사용한다.
- 실제 거래 적요에 포함된 `1Q`, `1분기` 문자열을 임의로 고치지 않는다.
- 이번 결함과 무관한 집계 계정 분류 규칙을 재설계하지 않는다.
- `testrun/`의 민감한 입력·출력 파일을 Git에 커밋하지 않는다.

## 5. 아키텍처와 책임 경계

### 5.1 `Period`: 유일한 기간 규칙 소유자

`app/domain/period_extract.py`의 `Period`가 다음 값을 제공한다.

- `start_month`: 항상 `1`
- `end_month`: `quarter * 3`
- `contains(year, month)`: 선택 연도이면서 `1 <= month <= end_month`
- 사용자용 라벨: 예) `2026년 2분기 누적 (1~6월)`

다른 모듈은 분기 번호로 시작월·종료월을 직접 계산하지 않고 `Period`의 공개 속성과
메서드만 사용한다.

### 5.2 원장 추출: 하나의 YTD 데이터 소스

기존 `extract_current_period(ledger, period)`를 유지하고, 성공한
`ExtractResult.df`를 집계와 상세 출력 양쪽에 전달한다.

결정론 파서 또는 AI 보조 파서가 확정한 `(year, month)` 목록은 필터링된
`DataFrame.attrs["period_year_months"]`에 행 순서대로 보존한다. 상세 작성기는 원본
날짜 문자열을 다시 해석하지 않고 이 메타데이터를 우선 사용한다. 따라서 AI가 구제한
날짜도 집계와 상세에서 동일하게 취급되며, 파서 간 드리프트가 생기지 않는다.

```text
/api/run(year=2026, quarter=2)
  -> Period(2026, 2)
  -> 원장 날짜 파싱 및 YTD 필터(2026-01~2026-06)
  -> 동일한 filtered_ledger
       |-> 38.x 집계 -> 특관자/39.2
       `-> 관련자 상세행 구성 -> 39.1
  -> 기간 정합성 검증
  -> 출력 안전성 검증
```

상세 출력 직전에는 방어적 검증을 한 번 더 수행한다. 날짜가 있는 상세 행 중
`period.contains()`를 만족하지 않는 행이 하나라도 있으면 명세서 다운로드를 차단하고
오류목록에 기간 불일치를 기록한다.

### 5.3 상세 행 모델과 분류

새로운 상세 행 구성 책임은 `app/domain/statement_detail.py`에 둔다. 이 모듈은
필터링된 원장, 거래처 정규화 매핑, 특수관계자 집합을 받아 `39.1`에 쓸 행만 반환한다.

- 거래처명이 정규화 매핑을 통해 특수관계자 집합에 포함된 원장 행만 채택한다.
- 표준 일자 표기는 Excel 날짜 타입으로 쓰고, 일(day)을 확정할 수 없는 AI 구제 표기는
  감사 가능성을 위해 원문을 보존한다. 금액은 숫자 타입으로 쓴다.
- `app/domain/columns.py`의 기존 키워드와 매칭 함수를 재사용한다.
- 한 행의 분류는 집계와 동일한 우선순위를 사용해 별도 규칙의 드리프트를 막는다.

`39.1`의 기존 열 계약은 유지한다.

| 열 | 값 |
|---|---|
| B | 매출/매입 분류 |
| C | 자금거래 분류 |
| D | 채권/채무 분류 |
| E | 수익/비용 분류 |
| F | 집계 버킷 계정과목 |
| G | 계정코드 |
| H | 계정과목 |
| I | 거래일자 |
| J | 적요 |
| K | 거래처코드 |
| L | 원본 거래처명 |
| M | 정규화된 회사명 |
| N | 차변 |
| O | 대변 |
| P | 잔액 |

### 5.4 템플릿 처리

`build_statement()`과 `fill_statement_template()`에 `Period`와 상세 행을 전달한다.

`39.1` 처리 순서는 다음과 같다.

1. 행 1~15의 기존 보고서 요약·헤더·서식을 유지한다.
2. 기존 템플릿의 행 16 이후 B:P 데이터 값을 모두 지워 과거 1분기 잔여 행을 제거한다.
3. 새 YTD 상세 행을 16행부터 쓴다.
4. 기존 상세행 스타일과 숫자/날짜 서식을 새 데이터 범위에 확장한다.
5. 상단 `SUMIF`/`SUMIFS` 요약 수식의 종료 행을 실제 마지막 상세행으로 갱신한다.
6. 예약된 빈 셀 `39.1!A1`에 `2026년 2분기 누적 (1~6월)`을 표시한다.

실제 적요는 원문 그대로 보존한다. 1~3월 거래의 적요에 `1Q`가 있어도 2분기 누적에
포함되는 정상 거래이므로 삭제하거나 `2Q`로 바꾸지 않는다.

`39.2` 값 주입과 `특관자`의 로컬 수식은 기존 방식을 유지하되, 그 입력 집계가 반드시
동일한 `filtered_ledger`에서 생성됐는지 파이프라인 수준 테스트로 검증한다.

## 6. 오류 처리와 안전장치

- 원장 날짜 미식별 또는 미파싱 잔존: 기존과 같이 다운로드 차단.
- 상세행에 선택 기간 밖 날짜 발견: 다운로드 차단 및 `오류목록.xlsx` 생성.
- 상세 필수 열 미식별: 조용히 빈 상세를 만들지 않고 다운로드 차단.
- 특수관계자 상세가 0건인 경우: 빈 데이터 구간과 0 합계는 허용하되 기간 라벨은 남긴다.
- 템플릿의 상세 데이터 제거 또는 수식 갱신 실패: 단순표 폴백으로 숨기지 않고 실패로
  처리한다. 잘못된 과거 분기 상세가 있는 파일보다 명시적 오류가 안전하다.
- 실제 거래 내용과 산출 금액은 화면·로그·테스트 출력에 노출하지 않는다.

## 7. TDD 검증 설계

구현 코드를 쓰기 전에 다음 실패 테스트를 먼저 추가하고 예상 원인으로 실패하는 것을
확인한다.

### 7.1 기간 단위 테스트

- 1Q: 1월과 3월 포함, 4월 제외.
- 2Q: 1월과 6월 포함, 7월 제외.
- 3Q: 1월과 9월 포함, 10월 제외.
- 4Q: 1월과 12월 포함.
- 모든 분기에서 전년도 12월과 다음 연도 1월 제외.
- `Q1 상세 행 집합 <= Q2 <= Q3 <= Q4` 누적 포함관계 확인.

### 7.2 상세 행 단위 테스트

합성 원장에 2026년 1·3·4·6·7월과 2025년 12월 행을 둔다.

- 2026년 2Q 상세에는 1·3·4·6월 행이 모두 존재한다.
- 7월과 2025년 12월 행은 없다.
- 관련자가 아닌 거래처는 없다.
- 날짜·차변·대변·잔액 타입과 B:P 열 매핑이 정확하다.

### 7.3 템플릿 회귀 테스트

- 템플릿 상세에 의도적인 `OLD_Q1_SENTINEL`을 둔 뒤 2Q 출력에서 완전히 제거되는지 확인.
- `39.1!A1`이 `2026년 2분기 누적 (1~6월)`인지 확인.
- 상단 요약 수식의 마지막 행이 새 상세 마지막 행과 일치하는지 확인.
- 실제 원장 적요의 `1Q` 문자열은 그대로 보존되는지 확인.
- 집계와 상세가 같은 필터링 원장 객체에서 만들어지는지 파이프라인 테스트로 확인.

### 7.4 `testrun/` 통합 검증

- `Period(2026, 2)`로 전체 파이프라인이 성공한다.
- 생성된 `39.1`의 날짜 있는 거래행은 모두 2026년 1월~6월이다.
- 4월~6월 거래가 한 건 이상 있어 1Q 출력이 아님을 확인한다.
- 7월 이후 거래는 없다.
- `특관자`/`39.1`/`39.2`의 수식 오류가 0건이다.
- 모든 시트를 렌더링해 표제, 헤더, 상세행, 합계가 잘리거나 겹치지 않는지 확인한다.
- 최종 산출물은 `testrun/당기_특관자_명세서_2026_2Q.xlsx` 하나만 생성한다.

테스트와 검증 로그에는 거래처명, 적요, 금액을 출력하지 않고 성공 여부와 건수 범주의
정합성만 남긴다.
